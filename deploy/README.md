# Релизы и деплой

Поведение курсов, расписаний и API описано в [документации курсов](../doc/courses.md).
Проверки и логирование — в [инструкции для разработки](../doc/development.md).

## Главные страницы преподавателей

Один контейнер `app` обслуживает все три сайта. `GET /api/public/site` доступен без
входа и выбирает контент по Host: `repit-ma.ru` (и `www.repit-ma.ru`) — Мария,
`okoroleva.repit-ma.ru` — Ольга, `mathegor.repit-ma.ru` — Егор.
Неизвестные домены возвращают 404.
Главная, вход, кабинет, регистрация и ссылки на API используют относительные
адреса, поэтому переходы сохраняют текущий поддомен. Авторизация хранится
отдельно для каждого origin. Поддомен выбирает публичную страницу и контакты,
а доступ к ученикам и курсам определяется существующим аккаунтом и его правами.
Публичные страницы пока не привязаны к числовым ID аккаунтов в базе.

Для включения поддомена на проде:

1. Добавить DNS-запись `A` для нового поддомена (`okoroleva` или `mathegor`), указывающую на тот же сервер, что
   и основной домен. Если используется `AAAA`, она тоже должна вести на этот сервер.
2. Выпустить и задеплоить приложение с поддержкой `/api/public/site`.
3. Добавить новый домен (`okoroleva.repit-ma.ru` или `mathegor.repit-ma.ru`)
   в существующий `/opt/repit-ma/Caddyfile`.
   [Caddyfile](Caddyfile) в этой папке — пример для конфигурации Compose:
   все домены проксируются в `app:8080`. Сохранить остальные серверные настройки.
   Не заменять Host адресом контейнера: по нему приложение выбирает преподавателя.
4. Проверить конфигурацию и применить её без остановки приложения:

   ```bash
   cd /opt/repit-ma
   docker compose exec caddy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
   docker compose exec caddy caddy reload --config /etc/caddy/Caddyfile --adapter caddyfile
   curl --fail https://repit-ma.ru/api/public/site
   curl --fail https://okoroleva.repit-ma.ru/api/public/site
   curl --fail https://mathegor.repit-ma.ru/api/public/site
   ```

Ожидаемые ответы: `{"teacher":"maria"}`, `{"teacher":"olga"}` и `{"teacher":"egor"}`.
Caddy получит сертификат для поддомена после настройки DNS и доступности 80/443.

Исходники публичных страниц, контент и локальная проверка описаны в
[документации публичных страниц](../doc/public-sites.md).

Workflow `.github/workflows/release.yaml` собирает исходники конкретного тега
`v0.0.1-RELEASE`, проверяет тесты и публикует образ
`ghcr.io/niksen111/repit-ma:0.0.1-RELEASE`. Обычный push ветки не деплоит сайт.
При push нового релизного тега деплой запускается автоматически.
Ручной запуск позволяет сначала опубликовать образ без деплоя.

## Первый запуск с уже существующим тегом

1. Закоммитить файлы workflow, scripts и deploy и запушить в основную ветку.
2. В GitHub → Actions → Release and deploy → Run workflow выбрать основную
   ветку, указать `v0.0.1-RELEASE`, оставить Deploy выключенным.
   Существующий тег пересоздавать не нужно. Собираются именно его исходники,
   поэтому изменения после тега в этот образ не попадут.
3. После успешной сборки проверить скачивание на сервере под пользователем deploy:

   ```bash
   docker pull ghcr.io/niksen111/repit-ma:0.0.1-RELEASE
   ```

   Для приватного образа пользователь deploy должен заранее выполнить
   `docker login ghcr.io -u Niksen111 --password-stdin`, передав через stdin
   PAT с read:packages. В workflow публикация использует встроенный GITHUB_TOKEN.
4. В `/opt/repit-ma/compose.yaml` заменить только image приложения на:

   ```yaml
   image: ghcr.io/niksen111/repit-ma:${APP_VERSION:?Set APP_VERSION in .env}
   ```

   Создать `/opt/repit-ma/.env` со строкой `APP_VERSION=0.0.1-RELEASE`.
   Файл compose.yaml в этой папке — полный образец серверной конфигурации.
   Сохранить текущие Caddyfile, data и имя Compose-проекта.
5. Повторить ручной запуск с тем же тегом и включённым Deploy.

## Настройка сервера и GitHub

Секреты репозитория: DEPLOY_HOST, DEPLOY_USER (deploy), DEPLOY_SSH_KEY,
DEPLOY_KNOWN_HOSTS. SSH использует порт 22. KNOWN_HOSTS должен содержать
проверенный ключ сервера. Токен GHCR не требуется сохранять в workflow.

Пользователь deploy должен иметь доступ к Docker без sudo, запись в
`/opt/repit-ma` и чтение всей папки data для резервной копии. На сервере нужны
Docker Compose v2, bash, flock, tar, curl и стандартные утилиты GNU.
Не менять владельца data на deploy: приложение работает с UID 10001.
Дать deploy доступ к чтению data через группу или ACL при необходимости.

Скрипт скачивает образ, останавливает app, архивирует data в backups,
запускает app и проверяет локальный HTTP и HTTPS сайта. Caddy не перезапускается.
Во время резервного копирования и старта app сайт временно недоступен.
После успеха обновляется APP_VERSION в .env. Если проверка не прошла,
workflow завершается ошибкой; автоматического отката базы нет.
Резервные копии не удаляются автоматически: контролировать свободное место.

## Еженедельная резервная копия в VK Cloud S3

На сервере `135.106.174.207` установлены `repit-ma-backup.timer` и
`repit-ma-backup.service`: каждое воскресенье в **04:00 Europe/Moscow**.
Хранилище — приватные объекты в бакете `repit-ma-backups-niksen`,
префикс `repit-ma/weekly/`, регион `ru-msk`.
**Проверено 26.10.2026:** сохранённый архив и свежий снимок успешно загружены в S3,
полностью скачаны обратно и сверены по SHA-256. Яндекс WebDAV больше не используется.
`Persistent=true` запускает пропущенное задание после включения сервера.
Это серверное задание systemd, оно не зависит от открытого чата или компьютера.

Скрипт [scripts/backup.py](../scripts/backup.py) использует SQLite Online Backup
через Python 3.12+ без остановки приложения. Для S3 нужен пакет `python3-boto3`.
Блокировка `.deploy.lock` общая
со скриптом деплоя: обновление приложения и снимок базы не выполняются одновременно.
Все текущие материалы и чеки хранятся в SQLite. Если появятся внешние файлы,
их нужно отдельно добавить в скрипт: еженедельный архив включает только базу
и `manifest.json` с версией приложения и SHA-256 базы.

Перед загрузкой скрипт проверяет `integrity_check`, `foreign_key_check` и базу,
извлечённую из архива. После загрузки полностью скачивает архив и сравнивает SHA-256.
Локальные архивы находятся в `/opt/repit-ma/backups/weekly/`, удалённые —
в `s3://repit-ma-backups-niksen/repit-ma/weekly/`. Файл `.uploaded` рядом с локальным
архивом содержит SHA-256 и адрес назначения и означает, что загрузка проверена.
При смене бакета или префикса старые архивы загружаются в новое место.
Непроверенные загрузки повторяются при следующем
запуске. При ошибке systemd повторяет задание через 15 минут, до четырёх запусков
за 12 часов. Ошибки видны в журнале; отдельные уведомления не настроены.
Автоматического удаления копий нет ни локально, ни в S3. Загрузка каждого объекта
использует ACL `private`, Content-MD5 и метаданные SHA-256; доступ — HTTPS/SigV4.
Размер одного архива ограничен лимитом S3 PutObject (5 ГБ); текущие архивы около 15 МиБ.

S3-ключи для задания хранятся в `/etc/repit-ma/backup.json` с правами `600`,
каталог — `700`; ключи не передаются аргументами процесса и не включаются в архив.
Формат настройки:

```json
{
  "access_key_id": "YOUR_ACCESS_KEY_ID",
  "secret_access_key": "YOUR_SECRET_ACCESS_KEY",
  "bucket": "repit-ma-backups-niksen",
  "endpoint_url": "https://hb.ru-msk.vkcloud-storage.ru",
  "region": "ru-msk",
  "project_dir": "/opt/repit-ma",
  "prefix": "repit-ma/weekly"
}
```

Для повторной установки сохранить скрипт в `/opt/repit-ma/scripts/backup.py`,
а [service](repit-ma-backup.service) и [timer](repit-ma-backup.timer) —
в `/etc/systemd/system/`. После создания защищённого файла настройки:

```bash
apt-get update
apt-get install -y python3-boto3
systemd-analyze verify /etc/systemd/system/repit-ma-backup.{service,timer}
systemctl daemon-reload
systemctl enable --now repit-ma-backup.timer
systemctl start repit-ma-backup.service
```

Тесты на Linux с Python 3.12+ и boto3:

```bash
python3 -m unittest discover -s scripts -v
```

Они проверяют восстановление строк SQLite из архива, отказ при повреждённом
скачивании, повтор загрузки и перенос копий при смене хранилища. Тесты используют
временную базу и S3 в памяти, производственные ключи и данные не читают.

Проверка и ручной запуск:

```bash
systemctl list-timers repit-ma-backup.timer --all
systemctl status repit-ma-backup.service
journalctl -u repit-ma-backup.service -n 50 --no-pager
systemctl start repit-ma-backup.service
```

### Восстановление базы

Выбрать архив из S3 либо из `backups/weekly`, распаковать в отдельный каталог.
Сверить SHA-256 `data/repit-ma.db` с `database_sha256` в `manifest.json`, выполнить
`PRAGMA integrity_check` и `PRAGMA foreign_key_check` через Python/SQLite.
В `manifest.json` также записана версия приложения: учитывать совместимость
этой версии с миграциями восстанавливаемой базы.

Восстановление выполнять в согласованное время простоя. Сначала остановить timer,
дождаться завершения активного backup service и получить эксклюзивную блокировку
`/opt/repit-ma/.deploy.lock` через `flock`. Остановить `app` командой
`docker compose stop app` из `/opt/repit-ma`. Сохранить **весь** старый каталог
`data` под отдельным именем, создать новый `data` с владельцем `10001:10001`
и правами `750`, положить проверенную базу как `data/repit-ma.db` с владельцем
`10001:10001` и правами `640`. Это исключает смешивание восстановленной базы
со старыми файлами WAL/SHM. Запустить `docker compose start app`, проверить сайт,
вход и данные. Освободить блокировку и включить timer обратно. Старый каталог
сохранить до подтверждения успешного восстановления.

## Следующий релиз

### Предпросмотр файлов

В материалах занятий, домашних заданиях, решениях и чеках рядом со скачиванием
доступен предпросмотр JPG/JPEG, PNG и PDF. Учитель, ученик и администратор видят
только файлы доступных им курсов. Файл загружается через существующий защищённый
API и открывается в окне приложения; сторонние сервисы не используются.
Просмотр PDF зависит от возможностей браузера; в окне есть ссылки для открытия
в новой вкладке и скачивания. Остальные форматы по-прежнему можно скачать.

Миграций, новых переменных окружения и изменений Caddy не требуется.
После обновления проверить предпросмотр материалов, файлов заданий, решений
и чеков под тремя ролями, включая ранее загруженные файлы и мобильный браузер.

### Календарь преподавателя

Вкладка `/calendar` использует существующие API расписания, статусов и оплаты,
изменений SQLite и новых переменных окружения нет. После обновления проверить
прямое открытие `/calendar`, переключение недель, отметки проведения и оплаты,
переход в выбранное занятие курса. На телефоне проверить прокрутку сетки,
закреплённые дни и часы, открытие и закрытие окна занятия. Календарь доступен
преподавателю и администратору; доступ к данным проверяет существующий API.

### Расписание, курс и личный комментарий

Расписание `/schedule` по умолчанию показывает будущие занятия, по 20 на страницу.
В курсе список содержит по 10 занятий и остаётся раскрытым после выбора.
У преподавателя содержание занятия находится над списком занятий.

Changeset `010-course-teacher-note` добавляет в `courses` поле `teacher_note`
с пустой строкой по умолчанию. Личная заметка преподавателя к ученику хранится
в SQLite и входит в существующую резервную копию `data`; новые тома и переменные
окружения не требуются. Заметка доступна преподавателю курса и администратору
через отдельный API и не включена в общие данные курса для ученика.

После обновления проверить сохранение и повторное открытие комментария с текстом
и ссылкой в курсе преподавателя. У ученика блок должен отсутствовать, а запросы
`GET` и `PUT /api/courses/{courseId}/teacher-note` — возвращать 403.
Проверить, что выбор другого занятия не сворачивает список и не сбрасывает его страницу.

### Статусы занятий, оплата и чеки

При запуске версии с учётом занятий Liquibase применяет changeset
`007-lesson-tracking-and-receipts`: добавляет поля исхода занятия и оплаты,
а также таблицу связей чеков. У существующих занятий статус определяется
по дате и времени; оплата по умолчанию не отмечена.

Время занятий интерпретируется как московское (`Europe/Moscow`), включая
сервер в Docker с другим системным часовым поясом. Дополнительные переменные
окружения и тома не нужны. Чеки сохраняются в SQLite, поэтому существующая
резервная копия каталога `data` включает их. Размер файла ограничен 25 МиБ.

После обновления проверить `/schedule` под преподавателем: смену статуса,
отметку оплаты и загрузку чека. В курсе ученика тот же чек должен скачиваться.
Изменять статусы, оплату и чеки ученик не может.

### Повторяющиеся занятия

Changeset `008-recurring-lessons` добавляет недельные расписания, слоты и журнал
созданных дат, а также необязательную связь занятия с расписанием. Существующие
занятия остаются разовыми. Все данные входят в SQLite и резервную копию `data`.

Changeset `009-edit-recurring-lessons` позволяет менять дни и время расписания.
Удалённые из расписания слоты сохраняются в журнале, чтобы их повторное добавление
не восстанавливало отменённые, перенесённые или удалённые занятия. Редактирование
применяется к дальнейшей генерации; уже созданные занятия сохраняются.

Генератор работает внутри приложения: ежедневно в 03:00 МСК и при старте
контейнера. Отдельный cron на сервере не нужен. При создании или возобновлении
расписания занятия на ближайшие семь дней создаются сразу. После простоя
дополняются только будущие даты. Журнал дат предотвращает дубликаты, в том числе
после переноса или удаления отдельного занятия и после перезапуска приложения.

По необходимости можно передать контейнеру переменные
`REPIT_MA_RECURRING_LESSONS_CRON` (по умолчанию `0 0 3 * * *`, МСК) и
`REPIT_MA_RECURRING_LESSONS_ENABLED` (по умолчанию `true`). Значение `false`
отключает фоновые и стартовые запуски; создание при сохранении расписания остаётся.

После релиза проверить под преподавателем кнопки на `/students`, создание
расписания с несколькими днями, наличие занятий на неделю вперёд, остановку
и возобновление. У ученика созданные занятия должны появиться в курсе.
При остановке можно отдельно выбрать отмену уже созданных будущих занятий.

В разработке использовать `0.0.2-SNAPSHOT`, перед выпуском — `0.0.2-RELEASE`.
Зафиксировать изменения версии в build.gradle и frontend/package.json коммитом.
Затем:

```bash
git tag v0.0.2-RELEASE
git push origin v0.0.2-RELEASE
```

Версия Docker-образа определяется тегом. Существующий первый тег может содержать
старую внутреннюю версию Gradle; это не препятствует сборке образа.
GitHub Release с описанием изменений можно оформить отдельно на тот же тег.
Не перемещать опубликованные теги: исправления выпускать новой версией.

Для отката образа указать предыдущий APP_VERSION в .env и выполнить
`docker compose pull app` и `docker compose up -d --no-deps app`.
Совместимость предыдущего приложения с миграциями базы проверить отдельно.
