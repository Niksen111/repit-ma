# Релизы и деплой

Workflow `.github/workflows/release.yaml` собирает исходники конкретного тега
`v0.0.1-RELEASE`, проверяет тесты и публикует образ
`ghcr.io/niksen111/repit-ma:0.0.1-RELEASE`. Обычный push ветки не деплоит сайт.
При push нового релизного тега деплой запускается автоматически.
Ручной запуск позволяет сначала опубликовать образ без деплоя.

## Первый запуск с уже существующим тегом

1. Закоммитить файлы workflow, scripts и deploy и запушить в основную ветку.
2. В GitHub → Actions → Release and deploy → Run workflow выбрать основную
   ветку, указать `v0.0.1-RELEASE`, оставить Deploy выключенным.
   Существующий тег пересоздавать не нужно. Собираются именно его исходники,
   поэтому изменения после тега в этот образ не попадут.
3. После успешной сборки проверить скачивание на сервере под пользователем deploy:

   ```bash
   docker pull ghcr.io/niksen111/repit-ma:0.0.1-RELEASE
   ```

   Для приватного образа пользователь deploy должен заранее выполнить
   `docker login ghcr.io -u Niksen111 --password-stdin`, передав через stdin
   PAT с read:packages. В workflow публикация использует встроенный GITHUB_TOKEN.
4. В `/opt/repit-ma/compose.yaml` заменить только image приложения на:

   ```yaml
   image: ghcr.io/niksen111/repit-ma:${APP_VERSION:?Set APP_VERSION in .env}
   ```

   Создать `/opt/repit-ma/.env` со строкой `APP_VERSION=0.0.1-RELEASE`.
   Файл compose.yaml в этой папке — полный образец серверной конфигурации.
   Сохранить текущие Caddyfile, data и имя Compose-проекта.
5. Повторить ручной запуск с тем же тегом и включённым Deploy.

## Настройка сервера и GitHub

Секреты репозитория: DEPLOY_HOST, DEPLOY_USER (deploy), DEPLOY_SSH_KEY,
DEPLOY_KNOWN_HOSTS. SSH использует порт 22. KNOWN_HOSTS должен содержать
проверенный ключ сервера. Токен GHCR не требуется сохранять в workflow.

Пользователь deploy должен иметь доступ к Docker без sudo, запись в
`/opt/repit-ma` и чтение всей папки data для резервной копии. На сервере нужны
Docker Compose v2, bash, flock, tar, curl и стандартные утилиты GNU.
Не менять владельца data на deploy: приложение работает с UID 10001.
Дать deploy доступ к чтению data через группу или ACL при необходимости.

Скрипт скачивает образ, останавливает app, архивирует data в backups,
запускает app и проверяет локальный HTTP и HTTPS сайта. Caddy не перезапускается.
Во время резервного копирования и старта app сайт временно недоступен.
После успеха обновляется APP_VERSION в .env. Если проверка не прошла,
workflow завершается ошибкой; автоматического отката базы нет.
Резервные копии не удаляются автоматически: контролировать свободное место.

## Следующий релиз

В разработке использовать `0.0.2-SNAPSHOT`, перед выпуском — `0.0.2-RELEASE`.
Зафиксировать изменения версии в build.gradle и frontend/package.json коммитом.
Затем:

```bash
git tag v0.0.2-RELEASE
git push origin v0.0.2-RELEASE
```

Версия Docker-образа определяется тегом. Существующий первый тег может содержать
старую внутреннюю версию Gradle; это не препятствует сборке образа.
GitHub Release с описанием изменений можно оформить отдельно на тот же тег.
Не перемещать опубликованные теги: исправления выпускать новой версией.

Для отката образа указать предыдущий APP_VERSION в .env и выполнить
`docker compose pull app` и `docker compose up -d --no-deps app`.
Совместимость предыдущего приложения с миграциями базы проверить отдельно.
